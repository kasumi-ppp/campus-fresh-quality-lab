## 3. 修复内容

### 3.1 购物车模块（`apps/df_cart/views.py`）

- 修改数量和删除条目时按“条目编号 + 当前登录用户”查询，查不到即判定为不可操作，返回 `ok: 0` 和明确提示。
- 加入购物车时校验数量必须大于 0，并检查商品是否未被逻辑删除、所属分类是否有效、库存是否大于 0。
- 重复加入同一商品时按累加后的数量与库存比较，避免绕过库存上限。
- 修改数量时校验数量上限，失败响应返回服务器当前保存的数量，供页面回填。
- 失败响应统一包含可理解的提示文本，不返回调试信息。

### 3.2 订单与金额（`apps/df_order/views.py`）

- 订单确认页和下单接口都改为按“条目编号 + 当前登录用户”过滤，并跳过失效商品。
- 订单总额改由服务器使用 `Decimal` 重新计算，商品小计加固定配送费 10.00 元，忽略浏览器提交的金额。
- 下单前校验收货地址非空，并把地址写入订单，形成下单时的收货信息快照。
- 订单号改为“秒级时间戳 + 微秒片段”，生成前检查是否已存在，避免重复编号覆盖订单。
- 同一次提交中的重复条目编号只结算一次。
- 业务失败返回 `{ok: 0, msg: 原因}`，未预期异常返回通用提示且不泄露堆栈。

### 3.3 库存与事务（`apps/df_order/views.py`）

- 库存扣减改为条件更新：仅当商品未删除、分类有效且库存仍然大于等于购买数量时才执行扣减。
- 命中行数不为 1 时判定库存不足并抛出业务异常，由事务整体回滚。
- 订单、订单明细、库存扣减和购物车条目的清理仍处于同一事务中，失败时不留下半张订单、部分明细或部分库存变化。

### 3.4 页面提示（`templates/df_cart/cart.html`、`templates/df_order/place_order.html`）

- 购物车页面按接口返回的 `ok` 判定结果，失败时回填服务器保存的数量、显示原因并重算合计。
- 删除成功后按条目编号移除对应行。
- 数量输入改为按整数解析，避免提交小数导致接口无法匹配。
- 订单确认页在地址为空时中断提交并跳转地址维护页。
- 订单确认页展示服务器返回的失败原因。
- 无可结算商品时以提示文字替代“提交订单”按钮。

### 3.5 公共模板（`templates/base_foot.html`、`templates/df_goods/ordinary_search.html`）

- 把已移除的 `{% load staticfiles %}` 改为 `{% load static %}`。

## 5. 既有测试的更新说明

`apps/df_order/tests.py` 中有两处断言固化了修复前的行为，随本次行为变更一并更新，均已在测试内注明原因：

1. `test_order_handle_success` 原先提交 `total: "33.00"` 并断言订单总额等于 33.00，相当于承认“服务器采信浏览器金额”。现改为保留该错误金额的提交值用于验证其被忽略，断言订单总额为服务器计算的 43.00（含配送费），并新增收货地址断言。
2. `test_order_handle_insufficient_stock` 原先断言响应体为纯文本 `库存不足`。现改为断言响应 JSON 的 `ok` 为 0 且 `msg` 含“库存不足”。

两个测试的用例原先未设置收货地址，本次按 C-ORD-003 补全，否则无法覆盖各自的目标场景。

## 6. 遗留问题与风险

1. `apps/df_order/views.py` 中的 `pay` 函数仍为空实现，且未配置路由。C-ORD-012 要求的演示支付状态尚未提供入口。
2. 并发验证以顺序提交覆盖“不超卖”的可观察结果，未使用真实并发压测；C-INV-004 的并发场景仍需在集成执行阶段用并发工具复核。
3. `daily_fresh_demo/urls.py` 及各应用 `urls.py` 仍使用 `django.conf.urls.url`，该接口在 Django 4.0 起被移除。当前环境为 Django 3.2.25 可正常运行，若按计划升级到 Django 5.2 需要一并改为 `re_path`。
4. `OrderInfo.odate` 使用 `auto_now=True`，语义上更接近创建时间的写法是 `auto_now_add=True`，本次未改动模型以避免额外迁移。
